# Independent releases and isolated local integration

The split services are the local development default. Immutable component images are published independently from deployment activation. Production already runs separate accounts, Hearts and Euchre services. The [deploy skill](../skills/deploy/SKILL.md) handles all current code in a selected app repository, component publishing, rehearsal and promotion. Its [operations reference](../skills/deploy/references/operations.md) describes the one-time reviewed host activation required before routine releases can deploy without Infra pin PRs. Preparing this capability preserves the running production pins and guarded rollback.

## Release one backend

In Cards, an `accounts-vMAJOR.MINOR.PATCH` tag runs `accounts-release.yml` and publishes only `ghcr.io/shmemcat/cards-accounts-api`. In Hearts and Euchre, a `game-vMAJOR.MINOR.PATCH` tag runs each repository's `game-release.yml`, publishing only `hearts-game-api` or `euchre-game-api`. Manual dispatch accepts an existing component tag. Game releases do not require the other repositories, frontend packages, account signing secrets, or the font package token.

Each workflow checks the service independently, builds and smoke-tests its image, refuses an already-published version tag, and publishes that version without promoting `latest`. The uploaded component JSON records the exact registry digest, source revision, account contract v1, owned schema revision, and explicit migration command. The source and version are also image labels and health metadata. Use the digest from this record when rehearsing or preparing an Infra pin.

The registry digest is read from Docker's [JSON manifest output](https://docs.docker.com/reference/cli/docker/buildx/imagetools/inspect/), then validated before the release record is written.

Legacy `v*` publishing is manual-only with an explicit acknowledgement, no `latest` promotion, and a refusal to overwrite existing versions. Retained combined artifacts remain available for compatibility work. See [manual legacy publishing](legacy-releases.md), including the release-branch and historical-tag limitations.

Cards also has a separate `gateway-vMAJOR.MINOR.PATCH` release for an immutable `cards-web` candidate. It publishes a gateway digest/source record without promoting `latest` or changing deployment pins. Use this when the split rehearsal needs newer proxy support while the live gateway must stay on its current release. It does not run a database migration.

Hearts and Euchre also support frontend-only `web-vMAJOR.MINOR.PATCH` candidates through `web-release.yml`. These publish only `hearts-cards-web` or `euchre-web`, refuse existing image versions, and leave `latest` and all API images unchanged. The final activation uses Hearts `web-v1.0.1` and Euchre `web-v1.0.0`. Hearts' candidate selects `NGINX_CONFIG=nginx.cards.conf` to serve private static files without requiring the legacy API hostname; the Docker default retains `nginx.conf` for existing releases.

Hearts, Euchre, and Golf cache npm package downloads (including Font Awesome Pro) and the Docker frontend dependency stage in GitHub Actions. `web-cache.yml` warms both caches on `main` when frontend or frontend workflow files change; it can also be run manually on `main`. Let it finish before tagging a frontend release. Warming the default branch matters because release tags can restore its caches, but cannot restore caches saved under another tag. Frontend release workflows and the retained Hearts and Euchre legacy release workflows use the same cache keys and Docker scope within each repository. The npm cache falls back to earlier lockfiles so unchanged packages can be reused when other dependencies change; Docker's dependency stage is reused when its inputs match. Authentication stays in the Actions secret and BuildKit secret mount; only npm's content cache is archived. A missing or evicted cache is populated by a normal install, so the first run still downloads packages. See [GitHub's cache access rules](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching#restrictions-for-accessing-a-cache) and [Docker's GitHub Actions cache](https://docs.docker.com/build/cache/backends/gha/).

The complete frontend/backend/rollback image set is reviewed in Infra's `activation-images.json`. Run the [final cutover and rollback rehearsal](cutover-rehearsal.md) against that manifest before selecting the explicit NixOS activation target. The normal Infra `nuttybox` target now preserves split ownership; returning to the combined owner requires the explicit guarded rollback target.

## Native local stack

Install Cards' test dependencies with `npm ci --ignore-scripts`. Install the three Python environments with `uv sync --locked --extra dev` in `cards/api`, `hearts/game-api`, and `euchre/api`. The two web environments need their normal dependencies for interactive development.

Run `npm run dev` from Cards, Hearts or Euchre after installing the sibling dependencies. Cards also retains the `dev:split` alias. Run only one copy of the shared runner. It starts the hub on port 3000, Hearts and Euchre web servers on 3001 and 3002, and accounts/Hearts/Euchre backends on 5100/5101/5102. Occupied ports are rejected; the runner never adopts an existing service. Stop it with Ctrl+C.

The default stack keeps its database, stable local signing/service keys, and file-only mail in `cards/.local/split-dev/`. It never adopts `.local/accounts.sqlite`, Hearts' instance database, or inherited database credentials. Its startup runs the three explicit service migrations in order. These migrations belong to this isolated data directory; the separate service images perform no startup migrations. Tests use newly created `split-rehearsal-*` directories instead of the persistent split development directory. Private account interfaces stay off the gateway. The shared old `/socket.io` transport returns a reload response in the default split stack; each game uses its canonical transport path.

Open `http://localhost:3000/`. Verification and recovery mail is available at `http://localhost:3000/__dev/mail/`. The game web proxies send account calls to accounts and game calls to their respective servers. Stopping this runner only stops processes it launched. For explicit combined compatibility work, Cards retains `npm run dev:combined`; it uses the previous data location and does not import or overwrite split data.

## Container rehearsal

`npm run test:images -- --build` builds local accounts, Hearts, Euchre, and gateway images and runs an isolated PostgreSQL rehearsal. It requires Docker, sibling backend checkouts, and the local Node dependencies. It does not build game frontends or require their font token. This is a backend/gateway rehearsal; use the native runner for the full interactive web applications.

`deploy/compose.split.yml` has no persistent database volume or published database/private-service port. It runs a fresh RAM-backed PostgreSQL database, serialized accounts/Hearts/Euchre migration jobs, and a grant job before workers start. Each worker uses a separate role with access to its own tables and sequences. Runtime probes assert that games cannot select account records and accounts cannot select Hearts data. The rehearsal gateway uses `deploy/split/proxy.conf`; production routing remains controlled by Infra.

The runner chooses a unique project name, fresh service keys, a new outbox under `.local/split-images-*`, and an available loopback gateway port. It does not read the developer `.env`. Cleanup removes only this rehearsal project's containers, network, and disposable volumes. A small `report.json` remains in that rehearsal directory; it contains image references, health versions/revisions, and check results, with no account credentials or mail links.

To rehearse published images, create a JSON object with exactly `accounts`, `hearts`, `euchre`, and `gateway` keys. Each value must be its component's `ghcr.io/shmemcat/<image>@sha256:<64 lowercase hex characters>` reference. Tags, `latest`, wrong-component images, and missing pins are rejected. No published digests are invented or supplied by default.

Run `npm run test:images -- --pins path/to/pins.json`. This mode pulls pinned images and never loads the source-build overlay or checks out sibling code. The Cards **Rehearse pinned split services** workflow accepts the same four digest references and runs this check using only the Cards checkout. Grant that workflow read access to the game packages if GHCR package visibility requires it.

The common probe registers and verifies a fresh local account, signs in once, checks shared Hearts preferences and both games' routes, exercises polling-to-WebSocket upgrade, restores saved games after each game's replacement, and confirms that the other game's process, connection, hand, turn, and score stay unchanged. It separately replaces accounts and the gateway, checks session continuity, and deletes the account through both cleanup callbacks. The existing full-match rehearsal remains available as `npm run test:hearts-server`.

Use `npm run test:images -- --build --config-only` to render/validate Compose without starting containers. Passing this check is not evidence of a container build or PostgreSQL execution.

Run `npm run test:postgres` for the source-built container checks plus a synthetic legacy backup/restore rehearsal. It applies the unchanged legacy migrations through `019` to a new database in the same disposable PostgreSQL container, seeds accounts/sessions/recovery records and both games' records, and restores a PostgreSQL dump into another new database. Both databases use a `hearts` schema to exercise the deployment's search-path shape. It then runs all three independent migrations twice, compares every seeded legacy table's record fingerprints, applies the runtime grants, and checks readiness using each restricted runtime role. Permission checks cover every table and owned sequence in both the fresh and restored schemas, including denied cross-service access and denied schema creation. The legacy source checkout is needed only for this opt-in rehearsal; published-image integration still needs no sibling checkout.

The backup contains generated test data only. This command never reads a developer or production database, and is separate from the required production-backup restoration before cutover. The report includes the synthetic record fingerprints and permission-check counts. PostgreSQL dumps stay inside the disposable container and disappear during cleanup.

For an approved read-only production dump, use `npm run test:production-restore -- --pins release/rehearsals/split-v1.0.0/pins.json`. It uses the existing SSH configuration, streams the archive into a separate RAM-backed database, and runs only the published images. The [production-restore runbook](production-restore-rehearsal.md) covers access, preservation checks, expiry accounting, privacy, and cleanup. `npm run test:restore-audit` checks the audit's rejection of valid-session loss using in-memory data.

## Promotion and rollback pins

To prepare a candidate manifest that changes one component, run `node scripts/component-pins.mjs old-pins.json hearts IMAGE@sha256:DIGEST candidate-pins.json` with the full Hearts reference from its release record. The utility validates all four image identities, preserves the other three pins, and writes a new file instead of overwriting the previous one. Use the same command with the previous digest to prepare a rollback candidate.

Rehearse the candidate manifest before promotion. Once the reviewed host release capability is activated, use `cards-release` with the actual published component records and a fresh host generation; routine application image updates require no Infra commit, PR or host rebuild. Infrastructure, networking, credentials and release-policy changes still use Infra review. Publishing workflows alone do not deploy containers or promote moving tags. A safe code rollback retains additive schemas, account revocation/deletion receipts, and exactly one writer for each game. Schema changes use the explicit maintenance/migration procedure before promotion.
